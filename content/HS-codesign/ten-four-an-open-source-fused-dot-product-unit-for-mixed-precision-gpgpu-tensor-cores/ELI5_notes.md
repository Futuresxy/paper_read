# Ten-Four: An Open-Source Fused Dot Product Unit for Mixed-Precision GPGPU Tensor Cores 通俗讲解

### 0. 整体创新点通俗解读

**痛点直击：开源界造不出像样的 Tensor Core，不是不想，而是“积木”本身不行**

NVIDIA 的 Tensor Core 快，是因为它内部那个点积运算是“一锤子定音”的硬件。但开源 GPGPU（Vortex、Ventus、Virgo）没这个奢侈，它们只能拿现成的**离散浮点库**（Berkeley HardFloat、FPnew）拼一个出来，结果处处难受：

- **延迟爆炸**：HardFloat 一个单元本身就要 **10 个 cycle**，Xilinx DSP IP 更是要 **31 个 cycle**。Tensor Core 本质是 [M×N] 网格的 K 元素点积，你拿一堆串起来的“乘完→存回→再取出来对齐→再归一化→再舍入”的流水线去拼，延迟层层叠加。
- **精度漏损**：每经过一次独立的 multiply 和 add，就多做一次**rounding**。浮点加法不满足结合律，中间结果每落地一次，误差就累积一分。这在长序列 K 维 reduction 里尤其致命。
- **资源浪费**：整数一条流水线、浮点一条流水线，两套 Tensor Core 执行单元还得配 arbiter 去调度——纯粹是花两份钱干一份活。
- **功能残缺**：2:4 结构化稀疏、OCP **Microscaling (MX)** 这些商业 GPU 已经标配的东西，开源界基本是空白。

---

**通俗比方：从“一摞小家电”到“一条流水线料理台”**

- 离散做法 = 你家里有一堆**独立小家电**：搅拌机打完倒进碗里，再端去烤箱，烤完再端去称重。每次“倒来倒去”都洒一点料（**rounding error**）、花时间（**latency**）、碗还占台面（**area / 寄存器开销**）。
- Ten-Four 的做法 = **中央厨房流水线**：食材从一头进去，成品从另一头出来，中间不落地、不过碗。

如果你熟悉 FMA，那这篇论文的本质一句话就能说清：**它把 "Fused Multiply-Add" 的融合思想，从 2 个操作数推广到了 N 个操作数的 Dot Product**——K 个乘积加上 addend C，全程只在**最后做一次 rounding**。这就是所谓 **FEDP (Fused Dot Product)**。再往上一层，Tensor Core 就是把这个 FEDP 摆成 [8×4] 的网格：

![](images/d175f5f32a315c3ef834a1b47354e3ca81e625c23289cc666254b18fd1943924.jpg) *Fig. 3: Vortex GPGPU SIMT Sub-Core with Tensor Core Unit Extension*

---

**关键一招：作者没有重造算术单元，而是把流程里“加法的位置”给扭了**

整篇论文最巧的几个逻辑转换，都可以归结为“把原本在**末端**做的事，搬到**最前面**，或者把两套流程**焊死成一套**”：

- **招式一：Addend C 提前进场（Early Addend Accumulation）**
  - 传统做法：先算完 Σ(A×B)，归一化、rounding 出个结果，再把 C 对齐、相加、再归一化、再 rounding——两次舍入，两套对齐硬件。
  - Ten-Four：C 的 exponent 从 **Stage-1 就参与“最大指数查找”**，它的 significand 和所有乘积一起对齐、一起进 CSA 压缩树。**全程只有 Stage-4 一次 rounding**。省了延迟，也省了精度损失。

- **招式二：让 Integer “搭浮点的顺风车”（Fused Integer Datapath）**
  - INT8/INT4 的乘加本来和浮点八竿子打不着，但作者发现二者共享绝大部分硬件（乘法器、CSA 累加树）。
  - 麻烦在于：浮点累加器只有 **25 + log₂(2K) 位**，装不下 32-bit 的整数 addend。作者的解法是**Addend 拆分**：低 25 位进 CSA 混着算，高 7 位（C_HI）**空手穿过流水线**，最后阶段再拼回去。代价近乎为零，却省掉了整整一套整数 Tensor Core。

- **招式三：格式归一——所有精度汇入同一条河**
  - FP16/BF16/TF32 的尾数都是 11 bit，干脆**共用一个 11×11 WTMUL**（BF16 补零进去）；FP8/BF8 用两个 4×4 乘完先内部加一轮。所有格式在 Stage-1 出口统一收敛到 **E8M25 中间表示**，后面三级流水线完全不感知输入格式。

- **招式四：稀疏不省计算，省电**
  - Inner-product 原语天然处理不了双侧稀疏（做 outer-product 又太贵，见下图）。

![](images/e5ae446cf2a14a982cf69ae35a8de3322c4b7c3520aa46c41faf821b5d8d5af5.jpg) *(a) Sparse-Dense interaction.*

  - 作者的务实取舍：既然零乘任何数都是零，那就**检测到输入为零的 Lane，直接 clock-gate**，进累加树前 AND 上 valid mask 清零。不省 FLOPS，但把**动态功耗**实实在在砍下来。

- **招式五：MX 的 scale “倒着用”**
  - 传统 MX 实现是先算 SoP，最后把两个 block scale 加到结果的 exponent 上。但 Ten-Four 因为 C 从第一步就掺进来了，**末端缩放这条路被自己堵死了**。
  - 解法依然是“搬到前面”：把 X^(A) + X^(B) 直接折进**每个元素的 exponent 加法**里。操作顺序反了，但 MX 规范明确允许 implementation-defined 的运算顺序，所以**完全合规**。

- **DSP 归零**是额外惊喜：纯 LUT 实现意味着部署不受 DSP 资源配额约束。

**一句话总结**

- 这篇论文的核心不是发明新算术，而是**做减法和挪位置**：把离散单元串联的“多次落地、多次舍入”流程，压缩成一条 4 级流水线；把加法、缩放这些原本在末端做的事**前置**，把整数和浮点两套硬件**熔成一套**。开源 GPGPU 第一次拥有了在延迟、面积、精度、功能上都能和商用 Tensor Core 对标的点积原语——而且它 100% 复现了 NVIDIA Ada Tensor Core 的数值行为（ULP=0），这在开源界是头一遭。

### 1. 4级混合精度融合点积浮点流水线（含加数早期累加）

**痛点直击**

- Tensor Core 里最频繁的操作就是 **点积+累加**：D = Σ(A×B) + C。看起来简单，但开源实现（如基于 **Berkeley HardFloat**、**FPnew** 的方案）把它拆成一串离散步骤：先乘、再逐个加、再对齐、再归一化、再舍入……
- 这种“离散拼积木”的做法有两个致命问题：
  - **延迟爆炸**：HardFloat 方案做一个 8 元素点积要 **10 个 cycle**，Xilinx DSP 更是要 **31 个 cycle**，而 Ten-Four 只需 **4 个 cycle**。
  - **舍入误差累积**：浮点加法不满足结合律，中间每做一次 2-operand 加法就舍入一次，误差像滚雪球一样越滚越大，最后和 NVIDIA Tensor Core 的结果对不上。
- 更隐蔽的一刀在 **C 的处理**上。传统做法是“先算完 Σ(A×B)，再单独把 C 加进去”——这一步额外需要一次**完整的对齐、归一化、舍入**，等于在流水线尾部又焊了一截尾巴，既拖慢时钟又多一次舍入。这就是典型的“顾头不顾尾”。

---

**通俗比方**

- 想象你开一家奶茶店，要算一整排原料的总成本，最后还要**加上上个月结转的账**（那个 C）。
- 传统做法是：店员先把所有新原料一笔一笔过收银机（每过一次都四舍五入一次），算完总数后，经理再专门跑一趟财务室，把结转账对齐汇率、再进收银机加一遍。
- **融合做法**是：结转账从一开始就和新原料**摊在同一张桌子上**，大家用同一把最大面额做基准对齐，一次算总账，只舍入**一次**。
- 关键的直觉在于：浮点加法最贵的操作是**对齐**——把所有数移到同一个量级。既然最后反正要加 C，为什么不让 C **一开始就参与“谁最大”的评选和排座次**？让它从流水线第一阶段就进场，而不是最后补票上车。

![](images/2ab21af127ec187a8cf03824f8a0157183a963fc8d7a363e0847c8e5b5ed288c.jpg) *Fig. 4: Ten-Four Mixed-Precision Fused Dot Product Microarchitecture*

---

**关键一招**

作者没有重新设计一套加法器，而是**把 C “提前塞进”了流水线的第一班车**，具体扭转了三处：

- **Stage-1（乘法+找最大指数）**：C 的 exponent 直接加入 **max exponent 识别电路**，和所有 A×B 乘积的指数一起参加“谁量级最大”的评选。传统设计里这个电路只服务乘积项，现在 C 享受同等待遇。
- **Stage-2（对齐）**：C 的 significand 和乘积项一起做移位对齐、转 2's complement、提取 **sticky bit**。大家被拉到同一量纲，为一次性大锅加做准备。
- **Stage-3（累加）**：所有项——K 个乘积 + C——一起进 **CSA（Carry-Save Adder）压缩树**。这是整个“融合”的精髓：**一次舍入机会都没有，误差只可能来自最后一步**。

再配合几个工程上的巧劲：

- **CSA + KSA（Kogge-Stone Adder）**：压缩阶段不做进位传播，把“进位链”这个经典长尾问题推迟到最后一刻，用并行前缀树快速收尾——这是 4-cycle 延速能压下来的关键。
- **加数拆分**：整数模式下 32-bit 的 C 塞不进 25-bit 宽的累加器，作者就把 C 拆成**低 25 位进 CSA、高 7 位（C_HI）走旁路**，最后在 Stage-4 拼回去——不扩累加器宽度，省了流水线寄存器的开销。
- **MX 支持的顺序反转**：因为 C 从第一阶段就在场，传统“算完 SoP 再把块缩放因子加到指数上”的路走不通（C 已经按原始指数对齐了）。作者的解法是把 scale factor **反转注入到每个元素的指数加法里**，从源头就把缩放“消化”掉——恰好 MX 规范允许自定义运算顺序，这一招完全合规。

**一句话总结**：传统设计把 C 当“事后补加的外人”，Ten-Four 把 C 当“点积家族的正式成员”，从流水线第一天起就一起选基准、一起对齐、一起进压缩树——**换来的是延迟减半、面积减四成、舍入只发生一次**，最终能和 NVIDIA Ada Tensor Core 做到 **100% 逐位一致（ULP=0）**。

### 2. 整数数据通路融合的加数拆分策略

**痛点直击 (The "Why")**

Ten-Four的核心卖点是“一条流水线通吃浮点和整数”。但问题来了：浮点流水线是为浮点数量身定制的，它的累加器（Stage-3的CSA树）宽度是精心算出来的——25 + log₂(2K)位。这个数字刚好够装下K个浮点乘积项加上加数C的**有效尾数**。

- 如果你想让INT8/INT4的整数点积也走这条流水线，麻烦就来了：**INT32的加数C是完整的32位**，没有任何“指数/尾数”结构可以裁剪。
- 天真做法是把累加器从25位加宽到32位。看起来只多7位，但代价会**乘性放大**：
  - CSA树的每一级都要变宽；
  - 最致命的是，**每一级流水线寄存器都要多存这7位**，而FEDP是并行Lane堆叠的设计（[8×4]网格），寄存器开销是成百上千倍复制的；
  - 换句话说，为了偶尔用到的整数模式，让浮点模式也被迫背上永远用不满的位宽——典型的“顾头不顾尾”。

---

**通俗比方 (The Analogy)**

这就像一条**混装货运传送带**：

- 浮点货物天生“会打包”——不管原来是FP16还是FP8，进流水线前都被压缩成统一规格的**25位标准箱**，传送带每个工位都按这个尺寸建。
- 突然来了个整数订单，货物是一个**32位的大件**，塞不进25位的箱子。
- 笨办法：把整条传送带加宽到32位——所有箱子、所有货架、所有工位全改规格，为了一个订单重造整条产线。
- 聪明办法：**把大件拆开运**。低25位装进标准箱混在普通货物里一起走传送带（反正累加器有现成的求和逻辑），高7位单独装个**小挎包**，让人直接拎着沿传送带走（只占一个7位的窄寄存器），到终点站（Stage-4）再合体。

![](images/2ab21af127ec187a8cf03824f8a0157183a963fc8d7a363e0847c8e5b5ed288c.jpg) *Fig. 4: Ten-Four Mixed-Precision Fused Dot Product Microarchitecture*

---

**关键一招**

作者没有加宽累加器，而是做了**位平面切分+ 旁路传播**，具体分三步：

- **拆**：把INT32加数C切成两半——低25位（进主流水线）和高7位（C_HI，走旁路）。
- **融**：低25位直接伪装成一个“乘积项”，和K个INT8乘积一起喂进Stage-3的CSA树免费累加。注意整数乘积本身也就十几位，25位累加器对它们绰绰有余，**完全复用，零改动**。
- **补**：唯一的漏洞是——低25位累加可能**溢出进位**。作者的处理是：在Stage-4做浮点归一化的**同时**（注意这个并行，不额外加流水级），把累加器的符号扩展进位加到C_HI上，重构出完整的高7位，再和低25位结果**拼接**，得到最终的INT32。

**妙在哪**：浮点的Stage-4本来就在做“提取幅值、移位”这类位操作，整数的“进位+C_HI”逻辑就搭在这趟顺风车上，几乎不增加关键路径。最终代价仅仅是每个Lane多7位流水线寄存器，而不是所有Stage的累加器和寄存器集体加宽7位。

---

**一句话总结**

- 别让流水线去适应数据，让数据去适应流水线——C的高7位“打了个车”绕过累加器，低25位“蹭公交”混进CSA树，终点站再会合。用**7位的旁路开销**，换掉了**全流水线加宽的乘性开销**，这就是整数/浮点融合能“几乎免费”的根因。

### 3. 稀疏通道掩码与时钟门控

**痛点直击**

深度学习模型里到处是零：剪枝后的 LLM 权重、稀疏激活、图神经网络的邻接矩阵。学术界一直想做 **Dual-Side Sparsity**（矩阵 A 和 B 两边都稀疏），但撞上了一堵墙：

- **Inner-product 的结构性缺陷**：点积是 A 的一行和 B 的一列做“内连接”。如果两边都稀疏，硬件必须先找到“两边都非零”的位置对齐才能乘——这本质上是个 **sparse-sparse inner join**，硬件代价极高。
- **NVIDIA 的妥协**：商业 Tensor Core（Ampere 及之后）只支持 **2:4 结构化稀疏**，且只作用在权重侧（sparse-dense 交互）。激活侧的稀疏性完全浪费。
- **前人的解法太贵**：Wang 等人的 DSTC 把点积改成 outer-product 来绕开 join 问题，但需要缓存整个 M×N 的中间部分积矩阵，**面积开销和计算密度损失**对数据中心 GPU 来说难以接受。

![](images/e5ae446cf2a14a982cf69ae35a8de3322c4b7c3520aa46c41faf821b5d8d5af5.jpg) *(a) Sparse-Dense interaction.*

![](images/9cb0e9279b3011e9725416bb1b7625af29737640f92b61e34872685b94e80a66.jpg) *(b) Sparse-Sparse interaction. Fig. 5: Inner-product primitive dual-side sparsity limitations*

于是出现了一个尴尬的局面：明明一堆零在白白耗电，硬件却只能照单全收。

---

**通俗比方**

想象一条流水线工厂，有 8 个工人（Lane），每人负责“乘法 + 对齐”两道工序，最后把 8 人的成果汇总到一台累加机器上。

- 传统做法：哪怕某工人手里的料是 **零**（乘出来必然是零），机器照样轰隆隆运转，电表照转——这就是**动态功耗**（switching activity）白白浪费。
- DSTC 的做法：为了跳过零，干脆把工厂改建成另一个布局——但厂房面积翻倍，不划算。
- Ten-Four 的做法很务实：**料是零的工人，直接让他停下手里的活儿（关灯、停机器），但人留在工位上**。到最后汇总那一步，把他工位上的产出强制置零塞进汇总机，保证结果不受影响。

一句话：**不追求算得更快，只追求零不耗电**。这是一次“功耗层面的稀疏性收割”，而非“吞吐层面的收割”。

---

**关键一招**

作者没有重构计算原语，而是利用了流水线的一个天然属性：**前几级的 Lane 计算是相互独立的（self-contained）**。具体做了两件事：

- **第一处：提前掐断**
  - 在流水线**最前端**做零检测（zero-detection），生成 input valid mask。
  - 某个 Lane 的输入为零 → 从 **Stage-1（乘法）** 开始就 clock-gate 它的 pipeline register。
  - 时钟一停，寄存器不翻转，乘法和对齐两个 Stage 的**全部开关功耗归零**——这是节省的大头。

- **第二处：出口消毒（关键细节）**
  - 时钟门控有个隐患：被冻结的寄存器里留着**上一轮的陈旧值**。
  - 到了 **Stage-3 累加器**，多 Lane 的结果要汇入 CSA 树，此时不再独立——陈旧值一旦混进去就是灾难性 bug。
  - 作者的解法：进累加器前，把第三个 pipeline register 的输出与 valid mask 做 **AND 门控**，强制被禁用 Lane 输出零值。就像汇总前把停工工人桌上的东西清空，只交白卷。

- **本质逻辑转换**：
  - 别人是“**为了稀疏，改变计算结构**”（outer-product）；
  - Ten-Four 是“**保留计算结构，只在功耗上做文章**”——用一根 AND 门 + 零检测电路的极小代价，换取动态功耗下降，且**不付任何面积/密度的税**。

![](images/2ab21af127ec187a8cf03824f8a0157183a963fc8d7a363e0847c8e5b5ed288c.jpg) *Fig. 4: Ten-Four Mixed-Precision Fused Dot Product Microarchitecture*

**一个值得记住的判断**：这项设计体现了典型的工程折中智慧——当一个问题（dual-sparse join）的“正确解”太贵时，退一步问“我能廉价地拿到这个问题的多少收益？”。Ten-Four 拿到的不是稀疏带来的吞吐加速，而是**功耗红利**，同时为未来真正的 unstructured sparse 硬件-软件协同设计留了接口。

### 4. Microscaling (MX) 格式的逆序缩放因子分解

**痛点直击**

先理解 MX (Microscaling) 格式到底在干什么：一个 block（比如 32 个元素）共享一个 2 的幂次方 scale factor (X)，元素本身只存低位宽的 mantissa（如 FP8/BF8）。这样既省内存，又比“一刀切”的全张量量化精度高。

- 标准实现思路（**deferred scaling，后置缩放**）：
  - 先把低精度元素的乘积老老实实累加起来，得到 Sum-of-Products (SoP)
  - 最后把两个 block scale 加起来（X^(A) + X^(B)），直接加到 FP32 结果的 exponent 上
  - 这就像“先加总账单，最后统一乘汇率”——便宜、干净
- 但这套流程撞上了 Ten-Four 的命门：
  - Ten-Four 的核心卖点就是 **fused**——FP32 addend C 从 **Stage-1** 就参与 maximum exponent 查找、从 **Stage-2** 就参与 alignment
  - 如果 scale 留到最后才加，那 SoP 在 pipeline 尾部才“恢复真实量级”，此时 C 早已在错误的量纲下和它对齐过了
  - 要兼容后置缩放，就得在 pipeline 尾部再补一轮 **对齐 + 归一化 + 舍入**——fused 设计辛苦省下的 latency 和 rounding error 又全赔回去了，等于白干

一句话：**不是 MX 不好，是 MX 的常规玩法和 Fused Dot Product 的管线“八字不合”**。

---

**通俗比方**

这就像**单位换算**。

- 你有一堆以“毫米”记账的货款（低精度 mantissa），要和一笔以“米”记账的大额存款（FP32 addend C）合并总账。
- **后置缩放**的做法：先把所有毫米数字加总，最后一步统一换算成米，再和存款合并。问题在于——你的会计流程（fused pipeline）要求**存款必须在开票那一刻就和所有货款放在同一张桌上对齐**。等加总完再换算，存款这桌已经散了。
- **作者的做法**：干脆在**每张货单开票的瞬间**，就把“毫米→米”的换算系数折进每笔金额里。这样一来，每一笔进入累加器的数字，从第一天起就和存款 C 生活在同一个量纲世界里——原有的对齐、累加、归一化流程**一个字节都不用改**。

---

**关键一招**

作者没有为 MX 另起炉灶，而是做了一次**纯粹的因式分解位置调换**——把 scale 从“公因子”变成“每项内嵌的指数偏移”。

- 数学上，利用 2 的幂乘法可交换的性质，把运算顺序调转：

  - 传统顺序：**先求和、后提公因子** → $(\sum p_i^{(A)} \cdot p_i^{(B)}) \cdot 2^{X^{(A)}+X^{(B)}}$
  - Ten-Four 顺序：**每项自带因子、直接求和** → $\sum (p_i^{(A)} \cdot 2^{X^{(A)}}) \cdot (p_i^{(B)} \cdot 2^{X^{(B)}})$

- 落到硬件上，具体是这一步被“扭转”了：
  - **Stage-1 的 exponent sum 电路**（原本算 $EXP_A + EXP_B + BIAS$ 转换项）
  - 现在只是**多加两个输入**：$X^{(A)}$ 和 $X^{(B)}$ 直接参与每个元素的指数加法
  - 由于 MX scale 是 E8M0 格式（纯 2 的幂），这个操作就是一次**整数加法，零乘法开销**
- 最妙的是**合规性兜底**：
  - MX 规范 (OCP Specification) 明确把“内部精度”和“运算顺序”定义为 **implementation-defined**
  - 所以虽然运算顺序和常规实现完全相反，结果却**依然 MX-compliant**——规范给硬件设计师留了后门，作者钻了进去

这招的精髓在于：**与其为了一项新功能改造整条 pipeline，不如找到一个数学上等价的形式变换，把新功能的成本压缩到 pipeline 入口处一个几乎免费的加法上**。这也是整个 Ten-Four 设计哲学的缩影——fused addend 处理、整数 addend 拆分 (C_HI 策略)、sparse lane clock-gating，全都是“不碰主干、四两拨千斤”的同一类操作。
